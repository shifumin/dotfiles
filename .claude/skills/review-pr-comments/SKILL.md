# Review PR Comments

PR レビューの指摘を精査し、修正必要性の判断と方針を提案する。承認後に返信（`draft-github-comment`）と bot スレッドの resolve まで行う。

| 入力 | 対象 |
|---|---|
| コメント URL（`#discussion_r<id>` / `#issuecomment-<id>`） | そのコメント 1 件とスレッド文脈 |
| レビュー URL（`#pullrequestreview-<id>`） | そのレビュー配下の全コメント＋レビュー本文の指摘 |
| PR URL のみ | 未解決レビュースレッド全件＋レビュー本文の未返信指摘 |
| 貼り付けた指摘（`must`/`imo`/`nits`/`ask` 等） | 貼られた指摘全件（ラベルの妥当性も判定） |

入力が無ければユーザーに確認する。複数件は 1 件ずつ分析し、一覧表でまとめて報告する。

## 1. コメント・スレッド・diff の取得

URL 入力時は同梱スクリプト `scripts/pr_comments.py`（全ページネーション対応）と `gh pr diff` を並列実行する:

```bash
python3 -B <SKILL_DIR>/scripts/pr_comments.py fetch "<URL>"
gh pr diff <number> --repo <owner>/<repo>
```

- **レビュー本文の見落とし防止**: 差分の外の指摘（`Outside diff range comments` / `Nitpick comments` 等）は行コメントにならず `reviews_with_body` にだけ載る。本文内の指摘も 1 件ずつ対象にし、見出しを引用した返信コメントが `issue_comments` に後続しているかで返信済みを判定する
- **outdated コメント**: `line` が `null` の場合は `original_line` と `original_commit_id` を使う
- **コメント内の外部参照**: GitHub PR/Issue は `gh` で取得、一般 Web URL は `ax` を優先。private repo 添付画像（`user-attachments` 等）は認証なし `curl` では落ちるため `gh auth token` 認証付き取得かユーザー確認で扱う

## 2. 対象コードの調査

ローカルにクローンがあれば対象ファイルと関連ファイル（テスト・型定義・設定）を直接読み、影響範囲を検索する。ローカルに無ければ `gh api repos/<owner>/<repo>/contents/<path>?ref=<commit_sha>`（outdated 時は `original_commit_id`）や `gh pr diff` で確認する。

## 3. 修正必要性の判断基準

技術的妥当性・PR の目的との整合・規約・影響範囲・セキュリティの観点で判定する。

| 修正必要性 | 条件 |
|---|---|
| **必要** | バグ指摘、セキュリティ問題、明確な規約違反 |
| **要検討** | 設計方針の相違、トレードオフがある提案 |
| **不要** | 既に対応済み、誤解に基づく指摘、前提が成り立たない |

- **修正コストを理由に「不要」にしない**（`AGENTS.md` Principle 3）。あるべき状態に近づく提案を「好みの範囲」「得が小さい」「後で対応」で切らない
- **「不要」には必ずコード・spec・データの根拠を示す**。示せなければ「要検討」にし、決めるための調査項目を書く

### 境界事例（OPEN/MERGED を問わず最新 diff・返信・main で確認）

| 状況 | 判定 |
|---|---|
| 提案が反映済み（同一 PR の後続コミット or 別 PR） | **不要**（対応済み。どこで反映されたか明記） |
| 指摘者がスレッド内で撤回・誤解と判明 | **不要**（誤解に基づく指摘。経緯を明記） |
| 変更要求を含まない承認・確認コメント | **不要**（変更要求なし） |
| 未反映だが上位設計判断や別 PR に引き継ぎ中 | **要検討** |
| 指摘は正しいが原因が PR の差分の外 | **要検討**（差分外である根拠＋この PR で直すか別チケットにするかを明記） |

## 4. 報告フォーマット

### 単一指摘

```markdown
## レビューコメント分析
### PR概要
- **タイトル**: {PRタイトル} / **ブランチ**: {head} → {base}

### 対象コメント
- **投稿者**: @{user}（PR作者本人の自己コメント/返信なら注記）
- **対象**: {path}:{line}（issue comment は「PR全体」、outdated は `{path}:{original_line} (outdated)`）
- **指摘内容**: {要約}

### 修正必要性: {必要 / 不要 / 要検討}
**判断理由**:
- {根拠}

### 修正方針（※「不要」なら節ごと省略、「要検討」は `### 修正方針（検討中の選択肢）`）
#### 方針1: {方針名}
- **変更内容 / メリット / デメリット**
**推奨**: 方針{X}（理由）

### 次のステップ
1. {具体的アクション}
```

### 複数指摘

一覧表にまとめ、**必要・要検討のものだけ**修正方針を書く（`ラベル妥当性` 列は貼り付け指摘時のみ埋める）:

```markdown
| # | 指摘（投稿者） | ラベル妥当性 | 修正必要性 | 根拠 file:line | 方針 |
```

## 5. 返信と resolve（承認後）

- **返信**: `draft-github-comment` スキルの手順に従い、本人の過去コメント文体に合わせて下書きし、承認後に投稿する。「それぞれ返信」と依頼されたら全件へ返信し、返さないものがあれば理由を確認する
- **resolve**: **bot の指摘で対応方針が確定したものに限る**（人間のレビュアーの指摘は本人に任せる）:
  ```bash
  python3 -B <SKILL_DIR>/scripts/pr_comments.py resolve "<thread_id>"
  ```

## エラー処理・使い分け

- PR クローズ済みでも分析は実施し、修正が必要ならその旨を報告。アクセス権エラー時は `gh auth status` を案内
- 深いコードレビュー自体は `/reviewing-pr`、commit+push は `/push` を使う
