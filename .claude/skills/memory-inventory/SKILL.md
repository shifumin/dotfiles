# auto memory の棚卸し

auto memory を、実測・鮮度検証・ユーザー合意のもとで整理する。
引数にプロジェクトパスまたは memory ディレクトリパスが渡された場合はそれを対象とし、無ければ現在のプロジェクトを対象とする。

## 前提と原則

- 毎セッション読まれるのは `MEMORY.md` のみ（先頭 200 行または 25KB の早い方で切り捨て）。トピックファイルは `MEMORY.md` の 1 行フックが唯一の入口なので、棚卸しの主眼は目次を正確かつ短く保つことにある
- `~/.claude/projects/` は git 管理外のため、ファイルは削除せず `_archive/` へ退避する
- 本文中の `[[name]]` はファイル名ではなく frontmatter の `name:` を参照する
- 起動時のリマインド条件は `.claude/hooks/memory-inventory-reminder.sh`（`.inventory-state.md` の更新時刻を参照）に委ね、毎日など過剰な再圧縮は行わない

## 承認レベル

| 操作 | 承認 | 理由 |
|:--|:--|:--|
| 目次の圧縮（詳細をトピック側へ移動） | 不要（事前共有のみ） | 情報が失われない |
| 事実の修正（実体・`gh` 等で検証済み） | 不要（事前共有のみ） | 根拠が客観的 |
| `name:` をファイル名へ揃え `[[ ]]` を張り替える | 不要（事前共有のみ） | 機械的で情報が失われない |
| `_archive/` への退避 | カテゴリ単位で確認 | 可逆 |
| ファイルの統合・本文の削除・書き換え | **必須** | 不可逆で内容が失われ得る |
| グローバル指示書（dotfiles）への昇格 | **必須** | 公開リポジトリかつ他端末へ波及する |

## Phase 0 — バックアップと前回状態の読み込み

まず memory ディレクトリを特定し、バックアップを取る。特定に失敗した場合は推測せずユーザーへパスを確認する。
システムプロンプトに Scratchpad directory がある環境では `--dest-dir` に指定し、無い環境では省略する（一時ディレクトリへ退避）。

```bash
/usr/bin/env python3 ~/.claude/skills/memory-inventory/scripts/inventory.py backup \
  [--dest-dir "<Scratchpad directory>"] \
  [--project "<path>" | --mem-dir "<path>"]
```

出力に `.inventory-state.md` の内容が含まれる場合、前回実行日と「解除条件つきで見送った項目」を確認し、見送り項目は Phase 2 で最優先に検証する。

## Phase 1 — 実測

```bash
/usr/bin/env python3 ~/.claude/skills/memory-inventory/scripts/inventory.py measure \
  [--project "<path>" | --mem-dir "<path>"]
```

確認する指標: `MEMORY.md` の行数・バイト数と上限（200行 / 25KB）に対する使用率、トピック件数、`type` 分布、`modified` 欠落、薄いファイル（本文5行以下かつ500B以下）、孤児、`name:` とファイル名の不一致、リンク切れ、未解決の `[[name]]`、150字超のフック行。

日付やスキル名など memory 以外の `[[ ]]` は未解決一覧から除外して読む。

## Phase 2 — 鮮度検証

全トピックファイルの本文を取得し、記述内容を外部の事実と突き合わせる（出力が大きい場合はファイル退避先を読む）。

```bash
/usr/bin/env python3 ~/.claude/skills/memory-inventory/scripts/inventory.py dump \
  [--project "<path>" | --mem-dir "<path>"]
```

検証観点:
- **ファイル・ディレクトリ・関数・フラグ名**: `ls` / `find` / `grep` で実在を確認する（消えた参照先が残ると毎セッション空振りする）
- **PR / issue 番号**: `gh pr view <n> --json state,mergedAt` / `gh issue view <n> --json state`
- **「◯◯まで注意」「未定」「マージ前に実施」型**: 解除・決着していないか最優先で確認し、正本ノートがあればそちらも読む
- **相対日付**（「来週」「今月中」など）: 絶対日付へ直せるか確認する
- **指示書との重複・矛盾**: グローバル `AGENTS.md` / `CLAUDE.md` / `.claude/rules/` やプロジェクトの指示書・skill と照合する。矛盾があれば指示書側が誤っている可能性も疑う

検証できなかった項目は「未検証」と明記し、検証済みと混ぜない。

## Phase 3 — 提案の組み立て

ファイル単位ではなく、判断の性質ごとにカテゴリへまとめる。

- **事実誤り** — 検証で誤りが確定したもの（承認不要だが必ず提示）
- **役割を終えた記録** — 完了した作業、決着した issue、期日切れ → 退避候補
- **近接クラスタ** — 同じ話題の複数ファイル → 統合候補
- **目次の肥大** — 150字超のフック行 → 圧縮候補
- **再取得可能** — コード・git 履歴・issue・指示書・skill を見れば分かるだけのもの → 退避候補
- **rules 向き** — プロジェクト非依存で今後も踏む知見 → 昇格候補（Claude Code / Codex 共通なら dotfiles の `AGENTS.md`、Claude 固有なら `.claude/rules/`。既存記述と重複すれば昇格しない）
- **中身が薄い** — 本文が数行で単独ファイルにする必要がないもの → 他へ統合候補

判断の線引き:
- **残す基準**: コード等から引き直せないもの（ユーザーの好み、判断の経緯、実測で分かった罠）は残し、引き直せるもの（構成、依存関係、過去修正の羅列）は退避する
- **`project` 型の扱い**: 恒久的な技術知見は `project` のままでよい（`reference` は外部リソースへのポインタ専用）

## Phase 4 — 合意

全ラウンドの合意がそろうまで Phase 5 へ進まない（途中で反映すると目次を何度も書き直すことになる）。

- **事前共有**: 最初のラウンド前に、承認不要の修正内容と、このラウンドで扱うカテゴリの根拠をチャット本文へ簡潔に書く（質問ダイアログだけで判断させない）
- **質問の粒度**: 質問ツール（無い環境ではチャットで番号選択）を使い、1ラウンド最大4問・カテゴリごとに1問・選択肢2〜4個で聞く。カテゴリ横断で「まとめて全部」は聞かない。4カテゴリを超える場合は目次に関わるものを優先してラウンドを分ける
- **選択肢の組み方**: 基本は「一括で実行」「個別に見る」「やらない」（一部のみ推奨なら「推奨のN件だけ実行」）。推奨を先頭に置き `(Recommended)` を付ける。説明欄に対象件数と代表ファイル名を書く
- **個別確認**: 「個別に見る」が選ばれたカテゴリは、次ラウンドで内訳と1件ごとの推奨を提示して確認する

## Phase 5 — 反映

合意された範囲のみ、次の順序で実行する（目次は最後に1回だけ書き直す）。

1. **事実の修正・相対日付の変換**: 相対日付は絶対日付へ直す（基準不明なら報告へ明記）
2. **統合・退避・昇格**:
   - **退避**: 先に恒久的な教訓を生き残る側へ移してから実行する。コマンドは次を使う（同名ファイルが `_archive/` にあっても上書きせずタイムスタンプ付きで退避する）:
     ```bash
     /usr/bin/env python3 ~/.claude/skills/memory-inventory/scripts/inventory.py archive \
       [--project "<path>" | --mem-dir "<path>"] <file.md> [...]
     ```
     退避後、他ファイルの `[[name]]` は吸収先へ張り替える（無ければ外す）
   - **統合**: 内容が厚い側のパスを残し、薄い側を見出し付きセクションとして末尾へ移してから薄い側を退避する
   - **本文の部分削除**: 削る箇所を `_archive/<name>_log_<YYYY-MM-DD>.md` へ切り出してから本体を書き直す
   - **dotfiles 昇格**: リポジトリ実体側を編集する（`~/.claude/` の symlink 経由は編集ツールが拒否することがある）。`AGENTS.md` 更新時は `.codex/build-agents.sh` を実行し、commit 時は編集ファイルだけ明示ステージする（`.claude/settings.json` を巻き込まない）。昇格済みの memory は退避する
3. **`name:` の統一と `[[ ]]` の張り替え**: `name:` をファイル名（`.md` 除く）へ揃え、リンク先を更新する
4. **目次の書き直し（`MEMORY.md`）**:
   - 1件1行・150字以内・`- [Title](file.md) — 一行フック` とし、削った詳細はトピックファイル側へ移す
   - フックには内容の要約ではなく「どういう時に開くべきか」を書く。近い話題は発動条件で書き分ける
   - 30件を超えたら開く場面ごとの見出し（`## 環境・ツール` など）で束ねる
   - 孤児のうち重要なトピックは目次へ追加する
   - ファイル書き込みツール（またはシェルの `>|`）で書き直す
5. **再計測**: `inventory.py measure` を再実行し、200行 / 25KB 以内かつリンク切れ・孤児・`name:` 不一致が無いことを確認する

## Phase 6 — 記録と報告

Phase 5 の全編集を終えてから（リマインダーフックが更新時刻を基準にするため）、`$MEM_DIR/.inventory-state.md` を更新する。

```markdown
最終実行: YYYY-MM-DD
MEMORY.md: <行数> 行 / <バイト数> bytes

## 解除条件つきで見送った項目
- <file>.md — <解除条件>（例: PROJ-1234 がマージされたら退避する）
```

最後にチャットで次を報告する:
- 触ったファイル数と操作の内訳（修正 / 圧縮 / 退避 / 統合 / 昇格）
- `MEMORY.md` の before / after（行数・バイト数・上限使用率）
- 見送った項目（解除条件があるものは `.inventory-state.md` にも記載）
- 未検証のまま残した項目
- バックアップのパス
