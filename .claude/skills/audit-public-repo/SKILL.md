# Public Repository Audit

公開リポジトリ（および公開予定のリポジトリ）を対象に、ファイル内容と Git 履歴から個人情報・業務情報・秘匿情報の混入を検出し、承認後に段階的な修復と履歴書き換えを支援する。

## 引数とモード

グローバルショートカットより本表の引数を優先して解釈する。

| 引数 / 指定 | モード | 検査対象 |
|---|---|---|
| 引数なし / `full` | 全量監査（既定） | tracked ＋ `.gitignore` 外の untracked ＋ 全 Git 履歴（全ブランチ・タグ） |
| `unpushed` | 未 push 監査 | ワーキングツリー変更（staged / unstaged / untracked）＋ `'@{upstream}..HEAD'` |
| `diff` | 差分監査 | ワーキングツリー変更（staged / unstaged / untracked）のみ |
| `staged` | コミット前ゲート | staged diff の追加行・新規ステージ済み危険ファイルのみ（Critical または PUBLIC/UNKNOWN 時の denylist 一致で exit 1。`push` スキルからも利用） |
| `<rev>..<rev>` / `<rev>` | 範囲監査 | 指定リビジョン範囲のコミット履歴 |

- `.gitignore` 対象は現行ツリーでは除外し、過去履歴への混入のみ検出する
- 非公開リポジトリでも公開前チェックとして続行し、レポート冒頭に `visibility` を明記する

## 設定ファイルとマスク原則

- **Denylist**: `~/.config/push-denylist.txt`（`push` スキルと共通、1 行 1 語・大文字小文字無視・`#` コメント可）。未作成なら警告を出しつつ検査を続行し、レポートで作成フォーマットを案内する
- **Allowlist（任意）**: `~/.config/public-audit-allowlist.txt`（1 行 1 ルール、`#` コメント可）。完全・部分一致リテラルのほか `re:<正規表現>`、`path:<glob>` に対応
- **マスク原則**: 検出した秘匿情報・個人情報・denylist 一致語は、チャット・レポートに生出力しない。必ず先頭・末尾だけ残した伏せ字マスク（例: `ghp_****abcd`, `ab****@ex****.com`）と、ファイル・行・コミット SHA で特定できるように報告する

## 処理フロー

### Phase 1 — 機械スキャン

対象リポジトリでスキャナを実行する。

```bash
/usr/bin/env python3 ~/.claude/skills/audit-public-repo/scripts/scan.py \
  --mode <full|unpushed|diff|range> [--range "<rev-range>"]
```

機械スキャンが検査する対象:
- 秘匿情報: 秘密鍵ヘッダ、主要サービスのトークン/API キー、JWT、認証情報付き URL、高エントロピーのシークレット代入、危険ファイル（`.env*`・鍵ファイル・資格情報 JSON 等、現行および削除済み履歴）
- 個人情報・業務情報: `~/.config/push-denylist.txt` 一致（ファイル・diff・コミットメッセージ・ブランチ/タグ名）、非 noreply メールアドレス（本文＋Git Author/Committer メタデータ）、携帯番号パターン、社内ドメイン/ワークスペース URL、プライベート IP
- ローカル固有情報: `/Users/<name>`・`/home/<name>`・`C:\Users\<name>` 絶対パス（リポジトリ owner の公開ハンドル一致は `Low`、不一致は `High`）、`.DS_Store` 等の OS ゴミファイル

出力件数が多く省略表示が出た場合は `--format json` で詳細を取得する。

### Phase 2 — AI 意味精査（文脈チェック）

機械スキャンでは拾えないリスクを、対象ファイルと履歴を実際に読んで精査する。

1. **機械スキャン検出箇所の真偽判定**: プレースホルダ・テスト用ダミー・公開ドキュメントの例示など誤検知を切り分ける（誤検知でも勝手に隠さず「誤検知候補」として件数と理由を短く添える）
2. **現行ツリーの文脈精査**: Phase 1 の `Worktree Text Inventory` にあるファイルを対象に、特にスキル・ルール・設定・スクリプト・ドキュメントを優先して読み、以下を探す（ファイルが多い場合は種別ごとに分割・並列で精査し、読み切れなかった範囲があればレポートに「未精査範囲」として明記する）:
   - **業務情報**: 会社名・部署名・チーム名、顧客・取引先名、社内システム/ツール固有名称、社内プロジェクト/リポジトリ名、社内 Slack チャンネル名、チケット番号（Jira / Linear / Backlog 等）、社外秘の業務フローや URL
   - **個人情報**: 本名・フルネーム・イニシャル、住所・最寄り駅・勤務地、個人 ID、個人的な予定・連絡先・家族/知人情報
   - **誤混入**: 一時メモ、業務ログ、デバッグ出力、ローカル専用設定
3. **コミットメッセージの意味精査**: 対象範囲のコミット一覧（`git log --oneline` 等）を確認し、社内チケット番号や業務固有名詞が混ざっていないか確認する

### Phase 3 — 重大度付きレポート出力

機械スキャンと AI 意味精査を統合し、以下の基準で重大度を分類して報告する。

| 重大度 | 基準 |
|---|---|
| **Critical** | トークン・API キー・秘密鍵・パスワード・認証付き URL・`.env` 等の資格情報ファイル（現行・履歴問わず） |
| **High** | 個人情報（本名・個人メール・電話番号等）・業務情報（会社名・社内 URL/ID・denylist 一致）・非 noreply の Git メタデータメール・公開ハンドルと異なるローカルユーザー名パス |
| **Medium** | プライベート IP・社内ドメイン候補・履歴上の要注意ファイル（`.sqlite`/`.dump`/`.bak` 等）・文脈上グレーな記述 |
| **Low / Info** | 公開ハンドルと一致するローカル絶対パス（`/Users/<owner>/...`）・`.DS_Store` 等の無害なゴミ・誤検知候補 |

レポートに含める項目:
1. 監査メタ情報（リポジトリ、`visibility`、スコープ、走査コミット数・ファイル数、denylist の読み込み状況）
2. 重大度別の検出一覧（種別 / 現行 or 履歴 / 場所（パス:行 or SHA） / マスク済み検出値 / 推奨対応）
3. 未精査範囲（バイナリや対象外とした範囲があれば明記）
4. denylist 未作成時の作成案内（例: `~/.config/push-denylist.txt` に 1 行 1 語で本名・会社名・社内ドメイン等を記載）

Critical / High / Medium が 0 件なら、確認済み範囲と Low/Info（あれば）を簡潔に報告して終了する。

### Phase 4 — 段階的な修復支援（承認必須）

承認なしでファイル編集・履歴書き換え・push を行わない。検出内容に応じて次の順でユーザーに提案し、承認を得た範囲のみ実行する。

#### 1. 漏洩済みクレデンシャルの即時ローテーション案内（最優先）

既にリモートへ push 済みのトークン・秘密鍵・パスワードが見つかった場合、**Git 履歴を書き換えても既に漏洩済みとみなすべき**である旨を明示し、該当キーの失効・再発行を最優先で依頼する。

#### 2. 現行ファイルの修正（承認後）

- プレースホルダ化（例: `YOUR_API_KEY`, `<company>`, `$HOME/...`）
- ローカル専用ファイル（`.gitignore` 管理下や `~/.config/`）への分離
- 誤混入ファイルの削除（`git rm` または `command rm -f`）と `.gitignore` 追記
- 許容する誤検知は、希望があれば `~/.config/public-audit-allowlist.txt` への追記を提案

#### 3. Git 履歴の書き換え（破壊的操作 — 別途明示承認必須）

履歴に Critical / High が残っている場合のみ、以下を段階的に進める:

1. **前提確認とバックアップ**:
   - `git filter-repo --version` を確認（未導入なら `brew install git-filter-repo` を案内）
   - 未コミット変更がないことを確認し、バックアップブランチを作成:
     ```bash
     git branch "backup/pre-audit-rewrite-$(date +%Y%m%d-%H%M%S)"
     ```
2. **書き換え内容の事前提示と承認**: 具体的なコマンドを提示してから実行する
   - 特定ファイルの履歴除去: `git filter-repo --invert-paths --path <path>`
   - 秘匿語・個人情報の履歴全体置換: 一時ファイル（`mktemp`）に `literal:<対象>==><置換語>` を書いて `git filter-repo --replace-text "$REPL"` 実行後、一時ファイルを即削除（`command rm -f "$REPL"`）
   - Author/Committer メール修正: 一時 mailmap ファイルで `git filter-repo --mailmap "$MAILMAP"` 実行後、一時ファイルを即削除
   - ※ `git filter-repo` は安全のため `origin` リモートを外す場合があるため、事前に `git remote get-url origin` を控えておき、書き換え後に必要なら復元する
3. **再スキャン検証**: 書き換え後に `scan.py --mode full` を再実行し、対象が現行・履歴の両方から完全に消えたことを確認する
4. **リモート反映（別途明示承認必須）**:
   - `git push --force-with-lease`（複数ブランチ・タグを含む場合は対象を明示）の影響（履歴改変、他端末での再 clone/reset 必要、GitHub のキャッシュ・PR・既存フォークには残り得る点）を説明し、明示的な承認を得てから実行する
   - 完了後、ローカルのバックアップブランチは確認後に削除するよう案内する（バックアップブランチが残っていると次回 `full` スキャンで再び検出される）
