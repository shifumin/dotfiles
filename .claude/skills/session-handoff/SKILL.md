# セッションの引き継ぎ

現在のセッションを、次のセッションが**同じ判断を再現でき、新しい局面でも同じ基準で判断できる**形に圧縮してチャットへ出力する。

引数を渡された場合は、それを次セッションの主題として扱い、引き継ぎ全体をその作業へ寄せる。

## 出力先はチャットのみ

ファイルを作らない。ユーザーがそのままコピーして次セッションの冒頭へ貼る前提である。

リポジトリ内へ書くと untracked が増えて作業ツリーが汚れる。scratchpad へ書くとセッション固有のパスなので次セッションから読めない。どちらも引き継ぎの手段として成立しない。

## 含める判断基準

基準は2つ。

1. **次セッションが同じ判断を再現できるか**
2. **セッションで扱わなかった局面が来ても、次セッションがユーザーと同じ基準で判断できるか**

1 からは、決定・見送った選択肢・ポインタの扱いが決まる。

- 決定は理由とセットで残す。理由がないと次セッションが同じ議論を最初からやり直す
- 見送った選択肢も理由付きで残す。書かないと次セッションが同じ案を再提案し、同じ検討を繰り返す
- 詳細はポインタで済ませる。PR・仕様書・commit・チケットに残っているものを本文へ再掲しない

2 からは、目的・背景、ユーザーの好み・制約、未解決の疑問・仮説を残すことが決まる。何をしたかは 1 だけで伝わるが、次セッションが新しい選択を迫られたとき、頼りになるのは 2 のほうである。決定の一覧は過去の局面にしか効かず、決定を生んだ基準は未来の局面にも効く。

長さの上限は設けない。判断の再現に要る情報を削るほうが損失が大きい。

ただし「セッションの要約」にはしない。時系列の経過や、途中で捨てた試行の詳細は、次セッションの判断に効かないため落とす。何が起きたかではなく、次に何を知っていれば動けるかで選ぶ。

例外は、考えが変わった経緯そのものが判断の理由になっている場合である。「最初は A で進めたが、X が判明して B に切り替えた」の X は、次セッションが A を再提案しないために要る。落とすのは判断に効かない作業ログ（試したコマンドの順番、何回目で通ったか）であって、理由の由来ではない。

## 秘匿情報を落とす

API キー、トークン、パスワード、個人情報、顧客データは引き継ぎに含めない。引き継ぎはチャットへ出力され、ユーザーがコピーして別の場所へ貼るため、そこに載せた値は複製されると考える。

次セッションがその値を必要とする場合は、値ではなく在り処を書く（例: 「認証情報は 1Password の項目名 X」）。除去したことに触れるのは、それが作業の続行に影響するときだけでよい。

## セクション構成

### 共通骨格（常に出す）

1. **目的・背景** — なぜこのタスクをやっているか、何が達成されたら終わりか、何がきっかけだったか。次セッションが「この作業はまだ要るか」「どこまでやれば十分か」を自分で判断する土台になる
2. **現在の状態** — 何がどこまで終わっているか。次セッションが最初に把握すべき事実
3. **残タスク** — 担当（自分 / ユーザー / 未定）を付ける。着手順が決まっているなら順序も書く。各項目に何のためにやるかを一言添える。目的が分かれば、前提が変わったときに次セッションがタスクを捨てたり差し替えたりできる
4. **下した判断と理由** — 見送った選択肢とその理由を含める
5. **ユーザーの好み・制約** — セッション中に分かった判断基準、こだわり、NG 事項、優先順位。決定そのものではなく、決定を生んだ基準を残す
6. **未解決の疑問・仮説** — まだ確かめていない仮説、迷っている点、崩れると判断が変わる前提
7. **詰まった箇所と回避方法** — 次に同じ作業をすると詰まる箇所と、その回避手段
8. **参照先** — チケット、ドキュメント、URL、次セッションが使うべき skill

5 と 6 は該当がなくても見出しを残して「なし」と書く。「ない」こと自体が情報で、書かないと次セッションは「制約は本当にないのか、書き忘れか」を判別できない。追加層の「なしとも書かない」ルールとはここが違う。

### 目的・背景が語られていないとき

セッション中に目的が一度も語られていなければ、出力前に AskUserQuestion で確認する。目的はユーザーの頭の中にしかないことが多く、引き継ぎを書く瞬間が、それを引き出せる最後の機会になる。推測で埋めると、次セッションはその推測を事実として引き継ぐ。

聞くのは目的だけでよい。好み・制約や未解決点は、出ていなければ「なし」で正しい。

### 追加層（セッション内容から判定して出す）

そのセッションで実際に使ったものだけを追加する。該当しなければセクション自体を出さない。「なし」とも書かない。使われなかったセクションの見出しはノイズになるだけで、次セッションの判断には効かないためである。

| セッションで起きたこと | 追加するセクション |
|---|---|
| git 操作（commit / push / PR 作成） | **ブランチ・PR** — ブランチ名、base、HEAD、PR URL、作業ツリーの状態 |
| テスト・lint・静的検査の実行 | **検証コマンド** — 実行したコマンドと結果。次セッションがそのまま再実行できる形で書く |

判定はセッションの内容から決める。「これは開発タスクですか」とユーザーに確認する必要はない。自分が何をしたかは自分が知っているためである。

## 「詰まった箇所」に何を書くか

タスク種別によって具体物が変わる。抽象的には「次に同じことをすると詰まる箇所と、その回避方法」である。

| タスク | 例 |
|---|---|
| 開発 | サンドボックスで拒否される操作、シェルのエイリアスによる silent failure（成功したように見えて何も起きない）、自動生成ファイルへ意図せず入る差分 |
| 調査・分析 | データの欠損や偏り、使えなかったクエリ経路、集計が前提にしている条件 |
| コーチング・対人 | 相手の制約、効かなかった提案、前提が変わった経緯 |

回避方法をセットで書く。「詰まった」だけでは次セッションが同じ時間を失う。

## memory への仕分け

`~/.claude/projects/<project>/memory/` に auto memory がある環境では、引き継ぎに書いたもののうち**恒久的に再発するもの**を memory へ移す候補として提案する。主な候補は「詰まった箇所と回避方法」と「ユーザーの好み・制約」に出てくる。

| 性質 | 行き先 |
|---|---|
| 環境・ツール・規約に起因し、今後も再発する罠 | memory（保存を提案する） |
| タスクを越えて変わらないユーザーの好み・判断基準 | memory（保存を提案する） |
| このタスク・この時点に限った事情 | 引き継ぎ本文のみ |

保存はユーザーの承認を得てから行う。提案する前に既存の memory と重複していないかを確認する。

memory へ移せば、同じ罠や同じ好みを毎セッション書き写さなくて済む。引き継ぎ本文が短くなるのは結果であって、目的は知見を1回で恒久化することにある。

## 手順

1. セッションを振り返り、共通骨格の8項目を埋める材料を集める
2. 目的・背景の材料がなければ、AskUserQuestion で確認する
3. git 操作とテスト実行があったかを確認し、追加層の要否を決める
4. 秘匿情報を落とす
5. チャットへ出力する
6. memory 行きの候補があれば、保存を提案する
