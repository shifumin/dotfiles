# スキルの診断と再設計

既存のスキルをゼロベースで見直し、元の意図や安全策を落とさずに、一貫した構造・自然な日本語・壊れにくい手順へ作り直す。

対象は引数（スキル名・パス）または会話で指定されたスキル。

## 手順

1. **対象と周辺を読む**: 正本ファイルを特定し、関連情報までまとめて確認する（下記「調査で集める情報」）
2. **改善ポイントを報告する**: 4つの観点で問題点を整理し、設計判断が分かれる点（2〜3点以内）だけユーザーへ確認する（すでに「お任せ」「全部直して」と指示があれば確認を省いて進む）
3. **ゼロベースで書き直す**: 継ぎ足し編集ではなく、全体を一貫した流れへ組み直す
4. **検証する**: スクリプトの構文・モック動作テスト、symlink・同期チェック、削ってはいけない要件の漏れ確認を行う
5. **結果と差分を報告する**: コミット・push はユーザーの指示があってから行う

## 調査で集める情報

編集前に必ず次を確認し、机上の空論や意図の取りこぼしを防ぐ。

- **正本と構成**: symlink を辿って正本パスを特定し、`SKILL.md` と付属ファイル（`scripts/`, `references/`, `examples/`）をすべて読む。サードパーティ（vendored）のスキルは直接編集せず、改善提案のみに留める
- **変更履歴**: 対象スキルの直近 git log を確認し、過去の不具合対応や継ぎ足された意図を把握する
- **参照先と規約**: 関連スキル（仕様の重複・ドリフト確認）、所属リポジトリの `AGENTS.md` / `CLAUDE.md`（記述規約・公開リポ制約）を読む
- **実物とツール仕様**: 対象 CLI の `--help` や過去の出力実例（あれば1〜2件）を確認し、実運用でのズレやバグを拾う

## 診断の4観点

### 1. 日本語・構造の掃除
- **重複の削除**: `description`・冒頭・本文・手順で同じルールや注意書きを何度も繰り返していないか
- **他スキル仕様のコピー排除**: 参照先スキルの数値（タイムアウト・リトライ回数）やコマンド仕様を再掲していないか。正本への参照に置き換える
- **不自然な表現の整理**: 硬い造語、抽象的な口癖、行動を変えないエッセイ調の解説、文体の混在（常体／である調）を平易で具体的な表現に直す
- **章立ての順序**: 実行手順が末尾に追いやられていないか。「手順 → 基準 → 出力形式 → 環境別処理／後処理」など上から順に実行できる並びにする
- **`description` の圧縮**: コンテキスト一覧を圧迫しないよう、役割・発火トリガー・起動条件に絞る

### 2. 仕様の穴・出力のブレ
- **出力フォーマット**: 見出しレベルやテンプレートが未定義で毎回揺れないか
- **空・例外時の扱い**: 各セクションが該当なしのとき「なし」と書くのか省略するのか、例外なく一貫しているか
- **セクション間の境界**: 似た項目同士で同じ事実が重複配置されないか、役割を1行で切り分けられているか
- **条件トリガーの網羅**: 分岐条件が狭すぎて実ケースが漏れていないか（例: git 操作に未コミット差分が含まれない等）
- **出力先間の整合**: チャット出力とファイル出力など複数経路があるとき、冒頭指示や本文が食い違っていないか

### 3. スクリプト・手順のバグと責務分離
- **分離の判断**: 長い `bash` ブロックや特定環境でのみ使う手順が `SKILL.md` を肥大化させていれば、`scripts/` や `references/` へ切り出す（非該当環境のノイズ削減とコマンド書き写しミス防止）
- **シェル処理の点検**:
  - リトライ上限に達したときに exit 0 で素通りしないか
  - `set -u` 下で未定義になり得る環境変数（`$TMPDIR` 等）を使っていないか
  - 固定一時ファイル（`noclobber` や並行実行で壊れる）を変数受けや `mktemp` にできないか
  - 連打や同時間帯で衝突する名前（秒なしの時刻など）になっていないか
  - 失敗時に調査用の識別子や直前出力が失われないか
  - macOS `/bin/bash`（3.2）や zsh 固有の罠（未クォートの `@{u}`、`rm`/`cp`/`mv` の `-i` エイリアス等）を踏んでいないか

### 4. 環境・マルチエージェント整合性
- 複数エージェントで共有されるスキルに、特定エージェント固有のツール名直書き（`AskUserQuestion`, `Write` 等）や固定値（`--kind claude` や単一環境変数での判定等）が混ざっていないか
- 逆に、単一エージェント専用のスキルならその前提が明確か

## 書き直しと検証のルール

- **価値を落とさない**: 既存の判断基準・エッジケース対策・安全策（削除禁止、再送禁止、確認必須など）を漏れなく引き継ぐ
- **公開リポ制約**: `dotfiles` などの公開リポジトリでは、実名・固有ホームパス・社内情報・機密を書かない（`~` や `$HOME`、プレースホルダを使う）
- **スクリプト検証**: 新設・変更したスクリプトには `chmod +x` を付け、構文チェック（`bash -n` 等）と、モックを使った正常系・リトライ・上限超過・異常系の動作確認を行う
- **同期確認**: リポジトリにスキル同期スクリプトがある場合は検証する（例: `.agents/sync-skills.sh --check`）

## Git 反映時（依頼された場合のみ）

1. 別件の未コミット変更を巻き込まないよう、対象ファイルだけを明示的に `git add` する
2. push 前に `git fetch` でリモートの先行コミットを確認する。同じスキルに先行変更があれば上書きせず統合してからコミットする
3. push 後に `HEAD` と上流ブランチ（`'@{u}'`）の一致を確認する
