# コンテキスト文書の診断と再設計

Skill・Memory・Rule・指示書・Output Style をゼロベースで見直し、元の意図や安全策を保ったまま、汚染語彙や冗長性のない簡潔な表現・一貫した構造・壊れにくい手順へ再設計する。

## モードと対象

| モード | トリガー | 対象 |
|---|---|---|
| **単発リファクタ** | スキル名・ファイルパス・ディレクトリパスを指定 | 指定対象と関連ファイル |
| **定期横断監査** | 引数なし、または「定期監査」「コンテキスト汚染チェック」「脱臭監査」 | グローバル設定・Output Style・現ワークスペース・全プロジェクト Memory（前回監査以降の差分＋静的シグナル検出ファイル） |

| 種別 | 主な対象 |
|---|---|
| Skill / Command | `SKILL.md`, `references/`, `scripts/`, `.claude/commands/*.md` |
| Rule / 指示書 | `AGENTS.md`, `CLAUDE.md`, `CLAUDE.local.md`, `GEMINI.md`, `.claude/rules/*.md`, `.claude/agent_docs/*.md` |
| Memory | `~/.claude/projects/<project>/memory/`（`MEMORY.md`・トピックファイル群） |
| Output Style | `.claude/output-styles/*.md`（ペルソナ同期元） |

## 調査で集める情報

編集前に次を確認する。

- **正本と構成**: symlink 先の正本パスを特定し、付属ファイル（`scripts/`, `references/` 等）まで読む。サードパーティ（vendored）ファイルは直接編集せず提案に留める
- **変更履歴**: git 管理下なら直近の `git log` で過去の不具合対応や追記の意図を把握する
- **周辺ルールと重複先**: 関連スキル・`AGENTS.md`・`CLAUDE.md`・`.claude/rules/`・`MEMORY.md` を確認し、重複・矛盾・記述規約（記述言語、公開リポ制約）を把握する
- **実物とツール仕様**: 対象 CLI の `--help` や実データを確認し、記述と実運用のズレを拾う

## 実行手順

### 定期横断監査モード

1. **プリスキャン**: 同梱スクリプトで前回監査以降の変更と静的シグナルを抽出する（全件表示は `--all`、他リポ追加は `--extra-root <dir>`）:
   ```bash
   python3 -B <SKILL_DIR>/scripts/scan_context.py --workspace . [--extra-root <dir>] [--all]
   ```
   - `CLEAN`（変更 0 かつシグナル 0）なら異常なしを報告し、手順 5 で監査日時を記録して終了する
2. **編集境界の仕分け**:
   - **個人管理（編集対象）**: Memory、`CLAUDE.local.md`、自身の `dotfiles` や個人リポジトリのファイル
   - **チーム共有リポジトリ（診断のみ）**: 共有の `CLAUDE.md` / `AGENTS.md` / `.claude/rules/` は直接編集せず、問題点と PR 用改善案のレポートのみ出す
3. **精査と再設計**: 抽出されたファイルを下の「単発リファクタ手順」に沿って診断・書き直し・検証する
4. **Output Style へのフィードバック**: 今回繰り返し検出された新しい汚染パターンがあれば、必要なときだけ `.claude/output-styles/*.md` の禁止ガード追記を提案する（毎回は変更しない）
5. **監査日時の記録**: 完了後に前回監査タイムスタンプを更新する:
   ```bash
   python3 -B <SKILL_DIR>/scripts/scan_context.py --mark-done
   ```

### 単発リファクタ手順

1. **対象と周辺を読む**: 「調査で集める情報」を集めて正本と前提を把握する
2. **改善ポイントを報告する**: 下の 4 観点で問題点を整理し、設計判断が分かれる点（2〜3 点以内）だけ確認する（「お任せ」「全部直して」の指示があれば確認を省いて進む）
3. **ゼロベースで書き直す**: 継ぎ足し編集せず、安全策を守りながら全体を一貫した構成へ組み直す
4. **検証する**: 種別ごとの構文・動作テスト、同期チェック、意図の漏れ確認を行う
5. **結果と差分を報告する**: コミット・push はユーザーの指示があってから行う

## 診断の 4 観点

### 1. 語彙汚染と表現の掃除
常時注入される Rule・指示書・Output Style・`MEMORY.md` は最優先で確認する。
- **簡潔さと情報密度**: 前置き・反復・回りくどい修飾を削り、1 文 1 要件で短く書く。一般常識や自明な手順は省く
- **不自然な造語・抽象ラベル**: 文脈なしでは意味がぼやける抽象表現（例: 「共通骨格」「追加層」「判断に効く」）を具体語へ直す
- **過剰強調・演説調**: 感情的・劇的な修飾語（誇張副詞や強い禁止語）を削り、事実と条件だけを淡々と書く
- **行動を変えないメタ語り・日記**: 現在の振る舞いを変えない解説や過去の作業ログ・日付エピソードを落とす
- **翻訳調・文体混在**: 常体／敬体の混在、指示書に不要なペルソナ口調、不自然な直訳を整える
- **記述言語の遵守**: 英語ファイル（`AGENTS.md` や `.claude/rules/*.md` 等）は英語のまま整える

### 2. 構造・重複・参照の整理
- **重複の削除**: ファイル内・ファイル間（`AGENTS.md` / `.claude/rules/` / `SKILL.md` / `MEMORY.md`）の同じルールの反復を削る（根拠が別なら両方残す）
- **他ファイル仕様のコピー排除**: 別スキルやフックの数値・コマンド仕様を再掲せず、正本への参照へ置き換える
- **構成のシンプル化**: 細分化しすぎた見出しや長い条件分岐を箇条書き・表へ畳み、使われなくなった分岐や互換記述を削る
- **章立ての順序**: 実行手順や重要ルールが末尾に埋もれないよう、上から読める並びへ組む
- **入口の圧縮**: Skill の `description` や `MEMORY.md` の 1 行フックをコンテキスト予算に収める

### 3. 仕様の穴・スクリプトのバグと責務分離
主に Skill・Command・付属スクリプトが対象。
- **仕様の曖昧さ**: 出力形式未定義、空・該当なし時の扱い、似た項目間の境界、分岐漏れ、複数出力先間の不一致を潰す
- **責務分離**: 長大な `bash` ブロックや特定環境専用手順が本文を肥大化させていれば、`scripts/` や `references/` へ切り出す
- **過剰設計の回避**: 1〜2 回しか使わない処理の無理な抽象化や要件外のオプションを足さない
- **シェル・スクリプト点検**:
  - リトライ上限到達時に exit 0 で素通りしないか
  - `set -u` 下で未定義になり得る環境変数（`$TMPDIR` 等）を使っていないか
  - 固定一時ファイル（`noclobber` や並行実行で壊れる）を `mktemp` にできるか
  - 連打や同時間帯で衝突する名前になっていないか
  - 失敗時に調査用の識別子や直前出力が失われないか
  - macOS `/bin/bash`（3.2）や zsh 固有の罠（未クォートの `@{u}`、`rm`/`cp`/`mv` の `-i` エイリアス等）を踏んでいないか

### 4. 環境・マルチエージェント整合性・Output Style
- 共有ファイルに特定エージェント固有のツール名（`AskUserQuestion`, `WebFetch`, `Read`/`Edit` ツール名、`scratchpad` 等）や単一環境前提の固定値が混ざっていないか
- 単一エージェント専用ファイルなら、その前提が明確か
- **Output Style 固有**: 簡潔さルールとの矛盾、象徴フレーズ発火条件の二重定義、作品固有セリフや他キャラ名の直書き、許可ルール単独での過剰拡張（禁止側ガード欠落）が無いか

## 種別ごとの安全策と検証

- **共通**:
  - 既存の判断基準・エッジケース対策・安全策（削除禁止、再送禁止、確認必須など）を落とさない
  - 公開リポジトリでは実名・固有ホームパス・社内情報・機密を書かない（`~`・`$HOME`・プレースホルダを使う）
- **Memory**:
  - git 管理外のため、編集前に一時ディレクトリ（`${TMPDIR:-/tmp}`）へ対象ディレクトリをバックアップする
  - 鮮度検証や `_archive/` 退避の棚卸しは `memory-inventory` に任せ、本スキルは語彙汚染・重複・構造のリライトに集中する
  - 編集後に `MEMORY.md` の上限（200 行 / 25KB）とリンク整合性を確認する
- **Rule / 指示書 / Output Style**:
  - 生成物があるリポジトリでは再生成とドリフト検証を行う（例: `dotfiles` の `AGENTS.md` / `output-styles/*.md` 更新時は `.codex/build-agents.sh` と `--check`）
- **Skill / スクリプト**:
  - 新設・変更したスクリプトには `chmod +x` を付け、構文チェック（`bash -n` / `python3 -B -c "import ast, pathlib; ..."`）とモックを使った正常系・上限超過・異常系テストを行う
  - スキル同期スクリプトがあるリポジトリでは検証する（例: `.agents/sync-skills.sh --check`）

## Git 反映時（依頼された場合のみ）

1. 別件の未コミット変更を巻き込まないよう対象ファイルだけ明示的に `git add` する
2. push 前に `git fetch` でリモートの先行コミットを確認し、同一ファイルに先行変更があれば統合してからコミットする
3. push 後に `HEAD` と上流ブランチ（`'@{u}'`）の一致を確認する
